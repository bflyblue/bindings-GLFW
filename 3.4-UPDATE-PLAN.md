# Plan: Update bindings-GLFW from GLFW 3.3.9 to 3.4

## Context

The `bindings-GLFW` Haskell package provides low-level FFI bindings to GLFW via
`hsc2hs` + `bindings-DSL`. It bundles a copy of GLFW C sources in `glfw/`
(currently 3.3.9). GLFW 3.4 was released 2024-02-23 with new API surface
(platform detection, custom allocators, new cursor shapes, etc.) and
architectural changes (runtime multi-platform support, null platform always
built). The goal is a clean branch with meaningful commits suitable for an
upstream PR.

## Source of truth

The official 3.4 release notes at https://www.glfw.org/docs/latest/news.html
were cross-referenced to compile this plan. The actual 3.4 `glfw3.h` header
should be diffed against the 3.3.9 header during implementation to catch any
constants not mentioned in release notes.

## Critical files

- `Bindings/GLFW.hsc` -- the single binding file (845 lines)
- `bindings-GLFW.cabal` -- package metadata, C source lists, flags
- `glfw/` -- bundled C source tree (`src/`, `include/`, `deps/`)
- `Test.hs` -- test suite with version checks
- `README.md` -- version reference

the Haskell binding declares `Ptr <GLFWwindow>` but the C header has always

header but were never bound. Fix these first so the 3.4 diff is clean.

**File:** `Bindings/GLFW.hsc`

Type fixes (change `Ptr <GLFWwindow>` to `Ptr <GLFWmonitor>`):
- `glfwGetWin32Adapter` (line 598)
- `glfwGetWin32Monitor` (line 599)
- `glfwGetCocoaMonitor` (line 641)
- `glfwGetX11Adapter` (line 675)
- `glfwGetX11Monitor` (line 676)
- `glfwGetWaylandMonitor` (line 758)

Also fix the corresponding error-stub signatures in the `#else` branches.

Missing constants (already present in glfw3.h 3.3.9, never bound):
- `GLFW_WAYLAND_LIBDECOR` (0x00053001)
- `GLFW_WAYLAND_PREFER_LIBDECOR` (0x00038001)
- `GLFW_WAYLAND_DISABLE_LIBDECOR` (0x00038002)

**Verify:** `stack build` (types are opaque so this won't break compilation)

### Commit 3: Update bundled GLFW C sources from 3.3.9 to 3.4

**Why:** Bulk-replace the vendored C tree. Kept as a separate commit so
reviewers can see it's a clean upstream import.

**Steps:**
1. Download GLFW 3.4 release:
   ```
   curl -L https://github.com/glfw/glfw/releases/download/3.4/glfw-3.4.zip -o /tmp/glfw-3.4.zip
   ```
2. Delete `glfw/src/`, `glfw/include/`, `glfw/deps/`
3. Copy from the release: `src/`, `include/`, `deps/` into `glfw/`
4. Optionally remove CMake-only files from `glfw/src/` that we don't compile
   (`CMakeLists.txt`, `*.pc.in`, `*.cmake.in`) -- but keeping them is harmless
   and matches historical practice

**Key file changes in 3.4 vs 3.3.9:**
- New: `platform.c`, `platform.h`, `posix_module.c`, `posix_poll.c`,
  `posix_poll.h`, `win32_module.c`
- The null platform files (`null_init.c`, `null_monitor.c`, `null_window.c`,
  `null_joystick.c`, `null_platform.h`) are now always needed (not just for
  OSMesa)
- `glad_gl.c` / `glad_vulkan.c` in `deps/` may be absent or restructured
  (these are only for GLFW's own examples, not the library)

**Note:** This commit alone will NOT build because `.cabal` still references old
file layout. That's expected.

### Commit 4: Update .cabal for GLFW 3.4 source file changes

**Why:** Align the Cabal build with the new source layout so the project compiles.

2. **Linux/FreeBSD section:**
   - Add: `glfw/src/posix_module.c`, `glfw/src/posix_poll.c`
   - Remove: `null_joystick.c` from FreeBSD-only block (now unconditional)

3. **macOS (darwin) section:**
   - Add: `glfw/src/posix_module.c`

4. **Windows (mingw32) section:**
   - Add: `glfw/src/win32_module.c`

5. **OSMesa flag block:** Remove the `null_*.c` files (now unconditional). Keep
   the flag for the `-D_GLFW_OSMESA` define if still referenced by 3.4, or
   remove the flag entirely if not.

6. **pkgconfig-depends:** Change `glfw3 == 3.3.*` to `glfw3 == 3.4.*`

**Verify:** `stack build` -- the C sources should compile and the existing .hsc

### Commit 5: Add GLFW 3.4 constants to Haskell bindings

**Why:** Expose the new constant values to Haskell consumers.

**File:** `Bindings/GLFW.hsc` -- add a "GLFW 3.4 additions" section.

New `#num` entries (~37, since Wayland libdecor was moved to commit 2):
- Error codes: `GLFW_CURSOR_UNAVAILABLE`, `GLFW_FEATURE_UNAVAILABLE`,
  `GLFW_FEATURE_UNIMPLEMENTED`, `GLFW_PLATFORM_UNAVAILABLE`
- Platform: `GLFW_PLATFORM`, `GLFW_ANY_PLATFORM`, `GLFW_PLATFORM_WIN32`,
  `GLFW_PLATFORM_COCOA`, `GLFW_PLATFORM_WAYLAND`, `GLFW_PLATFORM_X11`,
  `GLFW_PLATFORM_NULL`
- Cursor shapes (some are aliases for existing values, but new names):
  `GLFW_POINTING_HAND_CURSOR` (alias of `GLFW_HAND_CURSOR`),
  `GLFW_RESIZE_EW_CURSOR` (alias of `GLFW_HRESIZE_CURSOR`),
  `GLFW_RESIZE_NS_CURSOR` (alias of `GLFW_VRESIZE_CURSOR`),
  `GLFW_RESIZE_NWSE_CURSOR`, `GLFW_RESIZE_NESW_CURSOR`,
  `GLFW_RESIZE_ALL_CURSOR`, `GLFW_NOT_ALLOWED_CURSOR`
- Cursor mode: `GLFW_CURSOR_CAPTURED`
- Window hints: `GLFW_POSITION_X`, `GLFW_POSITION_Y`, `GLFW_ANY_POSITION`,
  `GLFW_MOUSE_PASSTHROUGH`, `GLFW_SCALE_FRAMEBUFFER`,
  `GLFW_WIN32_KEYBOARD_MENU`, `GLFW_WIN32_SHOWDEFAULT`, `GLFW_WAYLAND_APP_ID`
- ANGLE: `GLFW_ANGLE_PLATFORM_TYPE` + 7 enum values
  (`_NONE`, `_OPENGL`, `_OPENGLES`, `_D3D9`, `_D3D11`, `_VULKAN`, `_METAL`)
- Context: `GLFW_CONTEXT_DEBUG` (canonical name;
  `GLFW_OPENGL_DEBUG_CONTEXT` remains as alias with same value)
- Misc: `GLFW_X11_XCB_VULKAN_SURFACE`

**Implementation step:** Diff the 3.4 `glfw3.h` `#define` constants against
3.3.9 to catch anything not mentioned in release notes. Use:
```
diff <(grep '#define GLFW_' glfw-3.3.9/include/GLFW/glfw3.h | sort) \
     <(grep '#define GLFW_' glfw-3.4/include/GLFW/glfw3.h | sort)
```

**Verify:** `stack build`

## Verification strategy

### Build matrix

Each commit from 4 onward (once the project should compile) must be tested
across the full matrix. Commits 2-3 can be verified on Linux/X11 only since
they don't change the build configuration.

| Platform | Backend | Build tools | Flag overrides |
|----------|---------|-------------|----------------|
| Linux | X11 (default) | `stack build` + `cabal build` | (none) |
| Linux | Wayland | `cabal build` | `-f Wayland -f -X` |
| Linux | X11 + Wayland | `cabal build` | `-f Wayland -f X` |
| macOS | Cocoa | `stack build` + `cabal build` | (none) |
| Windows | Win32 | `stack build` + `cabal build` | (none) |

Also test on Linux with the `ExposeNative` flag:
- `cabal build -f ExposeNative` (X11 backend)
- `cabal build -f ExposeNative -f Wayland -f -X` (Wayland backend)

### Per-commit checks

- **Commits 2-3:** `stack build` on Linux/X11 (commit 3 is expected to fail)
- **Commits 4-6:** Full build matrix above
- **Commit 7:** Full build matrix + `stack test` / `cabal test` on each
  platform (tests require a display server; use `Xvfb` or similar on headless)
- **Final:** `stack haddock` / `cabal haddock` to verify documentation generates

## Key risks

1. **`GLFW_BUILD_*` guards** in new `.c` files -- highest risk for build
   failure. Must inspect `platform.h` from the 3.4 source to determine if
   explicit `-D` flags are needed in `.cabal`.
2. **Wayland protocol headers** -- GLFW 3.4 CMake generates C headers from
   `deps/wayland/*.xml`. If `wl_init.c` includes generated headers not present
   in the release tarball, we may need to generate them or find another approach.
3. **`glad_gl.c`/`glad_vulkan.c` removal** -- verify no GLFW library source
   (only examples) references symbols from these files.
4. **`glfwInitVulkanLoader` signature** -- takes `PFN_vkGetInstanceProcAddr`
   which is a function pointer; the `FunPtr` representation needs care.
5. **`GLFW_NATIVE_INCLUDE_NONE`** -- new preprocessor guard in 3.4 (not a
   runtime constant). No `#num` binding needed; the .hsc already controls
   native header inclusion via `#ifdef ExposeNative`.
6. **`GLFW_DOUBLEBUFFER` behavioral change** -- now a read-only window attribute
   in 3.4 (was settable). No binding change needed but worth noting for
   downstream consumers.
